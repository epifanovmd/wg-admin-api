# wg-admin-agent

Агент ноды WireGuard: маленький процесс на VPS, который приводит узел к
желаемому состоянию бэкенда и шлёт статистику. Без входящих портов — только
исходящие соединения к бэкенду (api-ключ со scope `wg-agent:<nodeId>`).

## Как работает

- **Связь** — постоянное WebSocket-соединение `/api/v1/wg-agent/link`
  (`internal/link`): бэкенд сам присылает desired state при изменении
  конфигурации и появлении команд, задаёт частоту статистики и подтверждает
  каждый тик номером. Неподтверждённые тики (до 600) хранятся и досылаются
  по порядку после переподключения — история на бэкенде без дыр. Живость —
  ping раз в 20 с; разрыв — переподключение с экспонентой. Если сервер или
  прокси не пропускают WebSocket (ответ на upgrade без канала, кроме 401/403/
  429/5xx), агент 10 минут работает по HTTP-протоколу (long-poll
  `GET /api/v1/wg-agent/state`, `POST stats|state|commands`) и снова пробует
  канал; `WG_AGENT_TRANSPORT=http` — только HTTP.
- **Конфигурация** — полный desired state (интерфейсы с пирами,
  IPIP-туннели, пробросы релея, команды).
  Применение идемпотентно: конфиги пишутся атомарно (0600), интерфейс
  поднимается `wg-quick up`; изменение interface-секции — down/up, изменение
  пиров — `wg syncconf` без разрыва соединений; удалённые интерфейсы
  опускаются. NAT-пресет (masquerade через egress-интерфейс) — в
  PostUp/PostDown. Итог — `POST state` (applied version, ошибки, статусы).
- **Релей**: IPIP-туннели (`ip tunnel`, rp_filter=0, MTU 1480; совпадающий
  по remote/адресу/MTU поднятый туннель не пересоздаётся — трафик релея не
  рвётся при других изменениях конфигурации) и пробросы (UDP точек
  подключения, UDP и TCP пробросов на внешние сервисы) в выделенных цепочках
  iptables `WG_ADMIN_PRE/POST` с разрешениями пересылки в `WG_ADMIN_FWD`
  (переход — первым в FORWARD: на хостах с Docker политика FORWARD — DROP, без
  них проброс молча режется). Цепочки пересобираются целиком, чужие правила не
  трогаются.
- **Автономность** — после каждого применения desired state сохраняется в
  `.wg-admin-desired.json` каталога конфигов (0600, без команд). При старте агент
  сначала применяет его, затем идёт к бэкенду: после перезагрузки хоста VPN и
  релей поднимаются, даже если бэкенд недоступен.
- **Пробросы на внешние сервисы** — UDP и TCP; для пути через туннель агент
  сам выбирает маршрут: `auto` уходит на прямой адрес после 3 неудачных проб
  туннеля подряд и возвращается при первой удачной, `tunnel`/`direct` —
  принудительно. Доменные адреса целей разрешаются в IPv4. После конфликта
  применение повторяется раз в 25 с.
- **Смена цели проброса** (аварийный переход, другая реплика, ручное
  переключение) сбрасывает потоки conntrack этого порта (`conntrack -D`):
  DNAT действует на первый пакет потока, а keepalive WireGuard держит
  запись — без сброса клиент оставался бы на прежней цели.
- **Туннели** — раз в ~10 с `ping -I wgtN` до дальнего конца каждого
  IPIP-туннеля и пакет размером MTU с DF; RTT, потери и MTU уходят со
  статистикой.
- **Откат при остановке** — по SIGTERM/SIGINT (`systemctl stop`, выключение
  хоста) агент откатывает созданное им по своему состоянию: WG-интерфейсы
  (`wg-quick down`, PostDown снимает NAT), туннели `wgt*`, цепочки
  `WG_ADMIN_*` и переходы на них. Чужое не трогается. Кэш конфигурации
  остаётся — при старте всё поднимается снова. Ручной откат —
  `wg-admin-agent cleanup`. SIGHUP — перезапуск без отката (переустановка,
  обновление): новый процесс застаёт интерфейсы и правила на месте и не
  пересоздаёт неизменное — клиенты не теряют связь.
- **Защита от чужого** — туннель не поднимается, если его подсеть
  пересекается с адресом на другом интерфейсе или к тому же хосту уже есть
  чужой IPIP-туннель; проброс не ставится на порт, который слушает другой
  процесс. Ошибка уходит в отчёт (`applyError`), периодический отчёт её не
  стирает.
- **Обновление без переустановки** — команда `agent-update` с sha256
  релиза: агент скачивает `GET /api/v1/wg-agent/binary/<arch>` своим ключом,
  сверяет хэш, атомарно подменяет свой бинарь (прежний — `<бинарь>.prev`),
  пишет отметку `.agent-update` в каталоге конфигов и завершается без отката
  (systemd перезапускает его на новом бинаре). Отметка снимается
  при первом успешном ответе бэкенда; три запуска без связи с бэкендом —
  возврат `.prev`. Версию, падающую раньше этой проверки, откатывает
  `ExecStartPre` службы — `/etc/wg-admin/boot-guard.sh`: пока лежит отметка,
  он считает запуски и на 5-м возвращает `.prev`. sha256 выполняющегося
  бинаря уходит в отчёте (`codeHash`).
- **Безопасность** — при `http://` бэкенде не на localhost агент пишет
  предупреждение в журнал: ключ и приватные ключи идут в открытом виде.
- **Повторы** — после ошибки связи экспонента 1–60 с со случайным разбросом.
- **Статистика** — `wg show all dump` + CPU, load 1/5/15, память, диск,
  аптайм, скорость сетевых интерфейсов (`/proc/net/dev`, без lo и Docker),
  conntrack. Частоту задаёт бэкенд: раз в секунду, пока открыта админка,
  иначе реже; смена частоты действует сразу. Тик несёт номер, идентификатор
  запуска и моменты сбора и отправки — бэкенд отбрасывает повторы и ставит
  точку на момент сбора. В отчёте (раз в минуту) — ещё режим
  WireGuard (`kernel`/`userspace`) и занятые UDP-порты (`/proc/net/udp{,6}`).
- **Команды** — только фиксированный набор: перезапуск интерфейса, хвост
  журнала агента (кольцевой буфер 2000 строк), обновление; срок выполнения —
  `timeoutSec` команды. Произвольные команды не выполняются: неизвестный тип
  завершается ошибкой.

Ядро без модуля wireguard — не проблема: если установлен `wireguard-go`,
`wg-quick` сам использует userspace-реализацию.

## Установка

Статический бинарь (Go, `CGO_ENABLED=0`, linux/amd64 и arm64) — служба
systemd. Бэкенд собирает бинари в своём образе и раздаёт установщик:

```bash
# на VPS (Linux с systemd), ключ — из ответа создания ноды или ротации ключа
curl -fsSL https://<бэкенд>/api/v1/wg-agent/install.sh | sudo sh -s -- --key <ключ>
# ключ из файла — не виден в списке процессов (ps) во время установки
curl -fsSL https://<бэкенд>/api/v1/wg-agent/install.sh | sudo sh -s -- --key-file <файл>
# удаление: откат созданного агентом, возврат хоста к состоянию до установки
curl -fsSL https://<бэкенд>/api/v1/wg-agent/install.sh | sudo sh -s -- --uninstall
```

Установщик ставит недостающие зависимости (`wireguard-tools`, `iproute2`,
`iptables`, `conntrack`, `ping`; apt/dnf/yum/apk; без модуля ядра —
`wireguard-go`; всё на месте — без `apt-get update`), включает ip_forward,
скачивает бинарь своей архитектуры по ключу агента и
сверяет sha256 из заголовка `X-Agent-Sha256`, пишет `/etc/wg-admin/agent.env`
(0600) и unit `wg-admin-agent.service` (`Restart=always` с паузой 1→30 с и
без лимита запусков; `KillMode=process` — перезапуск не завершает
`wireguard-go`; каталог конфигов `/etc/wg-admin/wireguard`). Работающий агент перезапускается сигналом HUP — без отката. Строки вывода —
с временем от начала (`▶ [12s] …`). Тот же скрипт выполняет установка по SSH
из админки (модуль wg-provision).

Журнал установки `/etc/wg-admin/install-state` — что было до неё: пакеты,
поставленные установкой (с зависимостями), исходные значения forwarding,
загруженные ей модули `wireguard`/`ipip`. Пишется один раз, повторная
установка его не меняет. `--uninstall` возвращает только записанное: пакеты
удаляются, если не нужны другим (`iptables`/`conntrack` при Docker —
остаются), forwarding — к исходному значению (выключение — не при работающем
Docker), модули выгружаются, если свободны. Полный снимок `/etc` или
iptables не делается: восстановление затёрло бы изменения Docker и другого
ПО после установки. Без журнала хост остаётся как есть — удаляется только
своё (`99-wg-admin.conf`).

```bash
wg-admin-agent            # запуск (по умолчанию)
wg-admin-agent version    # версия и sha256 бинаря
wg-admin-agent cleanup    # откат созданного агентом
journalctl -u wg-admin-agent -f
```

## Окружение

| Переменная                                                  | Назначение                                               |
| ----------------------------------------------------------- | -------------------------------------------------------- |
| `WG_AGENT_BACKEND_URL`                                      | URL бэкенда (обязательно)                                |
| `WG_AGENT_KEY`                                              | api-ключ агента (обязательно)                            |
| `WG_AGENT_CONFIG_DIR`                                       | каталог конфигов и состояния (`/etc/wg-admin/wireguard`) |
| `WG_AGENT_TRANSPORT`                                        | `auto` (канал, HTTP при неподдержке) или `http`          |
| `WG_AGENT_POLL_WAIT_MS`                                     | ожидание long-poll по HTTP (25000; бэкенд ограничивает)  |
| `WG_AGENT_STATS_INTERVAL_MS`, `WG_AGENT_REPORT_INTERVAL_MS` | статистика до указания бэкенда (2000) и отчёт (60000)    |

## Разработка

```bash
cd agent
go test ./... && go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \
  -ldflags "-s -w -X main.version=$(cat VERSION)" \
  -o dist/wg-admin-agent-linux-amd64 ./cmd/wg-admin-agent
../scripts/go-agent.sh test   # то же в контейнере golang (версия Go из go.mod)
```

Изменение кода агента (кроме тестов и README) требует поднять
`agent/VERSION`: CI сверяет с последним тегом `v*`
(`scripts/check-agent-version.sh`, там же — ветка Go в Dockerfile-ах против
`go.mod`).

Версия — `agent/VERSION`. Протокол — `internal/protocol`, зеркало
`src/modules/wg-agent/wg-agent-protocol.ts` (менять синхронно). Файлы
состояния и отпечаток interface-секции (`Fingerprint`) имеют фиксированный
формат: его смена сбросит состояние или перезапустит интерфейсы при
обновлении.

Агент в контейнере — только для smoke-стенда (`test/smoke`, см. корневой
README): `test/smoke/Dockerfile.agent` — тот же бинарь поверх Debian с
утилитами, каталог конфигов `/etc/wireguard`.
