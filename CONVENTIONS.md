# Project Conventions

Единые обязательные соглашения по написанию кода. Этот документ отвечает на вопрос
«как писать код» и не описывает конкретные модули приложения.

- Архитектурная модель, слои и границы: [ARCHITECTURE.md](ARCHITECTURE.md).
- Выбор места для нового кода: [MODULE-CHEATSHEET.md](MODULE-CHEATSHEET.md).
- Чистый код, SOLID и паттерны: [CLEAN-CODE.md](CLEAN-CODE.md) и
  [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).
- Если правило расходится с автоматически проверяемой конфигурацией, фактическое
  поведение определяется конфигурацией линтера, а расхождение устраняется отдельно.

## 1. Область действия

Правила распространяются на весь написанный вручную код приложения.

Не редактируются вручную:

- сгенерированный файл маршрутов и OpenAPI-спецификация;
- сборочные артефакты;
- применённые миграции (новое изменение схемы — новая миграция).

Требования внешнего фреймворка или генератора имеют приоритет только для
принадлежащих ему файлов. Исключение должно быть локальным и задокументированным.

## 2. Именование директорий и файлов

Папки — в `kebab-case`, имя модуля — существительное предметной области или название
подсистемы.

| Содержимое                     | Соглашение                        | Пример                                    |
| ------------------------------ | --------------------------------- | ----------------------------------------- |
| Сущность ORM                   | `<name>.entity.ts`                | `<feature>.entity.ts`                     |
| Репозиторий                    | `<name>.repository.ts`            | `<feature>.repository.ts`                 |
| Сервис                         | `<name>.service.ts`               | `<feature>.service.ts`                    |
| Контроллер                     | `<name>.controller.ts`            | `<feature>.controller.ts`                 |
| Модуль                         | `<name>.module.ts`                | `<feature>.module.ts`                     |
| Enum-ы и константы домена      | `<name>.types.ts`                 | `<feature>.types.ts`                      |
| Доменные ошибки                | `<name>.errors.ts`                | `<feature>.errors.ts`                     |
| Права модуля                   | `<name>.permissions.ts`           | `<feature>.permissions.ts`                |
| Доступ к сущности с владельцем | `<name>.access.ts`                | `<feature>.access.ts`                     |
| Обработчик очереди задач       | `<aspect>.job.ts`                 | `<feature>-cleanup.job.ts`                |
| DTO                            | `dto/<name>.dto.ts`               | `dto/<feature>.dto.ts`                    |
| Схема валидации                | `validation/<action>.validate.ts` | `validation/create-<feature>.validate.ts` |
| Доменное событие               | `events/<name>.event.ts`          | `events/<feature>-created.event.ts`       |
| Обработчик реального времени   | `<name>.handler.ts`               | `<feature>.handler.ts`                    |
| Слушатель событий              | `<name>.listener.ts`              | `<feature>.listener.ts`                   |
| Bootstrapper                   | `<name>.bootstrap.ts`             | `<feature>.bootstrap.ts`                  |
| Middleware                     | `<name>.middleware.ts`            | `<purpose>.middleware.ts`                 |
| Guard                          | `<name>.guard.ts`                 | `<purpose>.guard.ts`                      |
| Тест                           | `<file>.test.ts` рядом с кодом    | `<feature>.service.test.ts`               |
| Public API                     | `index.ts`                        | `modules/<feature>/index.ts`              |

Суффикс файла обязан совпадать с ролью класса внутри: в `*.service.ts` нет
контроллеров, в `*.entity.ts` нет enum-ов.

## 3. Именование в коде

| Сущность                  | Стиль                                  | Пример                         |
| ------------------------- | -------------------------------------- | ------------------------------ |
| Класс                     | `PascalCase` + суффикс роли            | `FeatureService`, `FeatureDto` |
| Сущность ORM              | `PascalCase`, единственное число       | `Feature`                      |
| Таблица                   | `snake_case`, множественное число      | `features`                     |
| Колонка в БД              | `snake_case`                           | `created_at`                   |
| Поле сущности             | `camelCase`                            | `createdAt`                    |
| Индекс                    | `IDX_<TABLE>_<COLUMNS>`                | `IDX_FEATURES_USER`            |
| Интерфейс                 | `I` + `PascalCase`                     | `ICreateFeatureBody`           |
| Тип-алиас                 | `T` + `PascalCase`                     | `TPermission`                  |
| Enum                      | `E` + `PascalCase`, значения — строки  | `EFeatureStatus`               |
| Const-объект вместо enum  | `PascalCase`, `as const`               | `FeatureRoles`                 |
| Доменные ошибки           | `<Feature>Error`, код `<PREFIX>_<KEY>` | `FEATURE_NOT_FOUND`            |
| Права модуля              | `<Feature>Permissions`                 | `FeaturePermissions.MANAGE`    |
| Очередь задач             | `домен.действие` в kebab-case          | `feature.cleanup`              |
| Событие                   | `<Subject><PastParticiple>Event`       | `FeatureCreatedEvent`          |
| Схема валидации           | `<Action><Subject>Schema`              | `CreateFeatureSchema`          |
| DI-токен                  | `SCREAMING_SNAKE_CASE` Symbol          | `SOCKET_HANDLER`               |
| Приватное поле класса     | `_camelCase`                           | `_featureRepo`                 |
| Метод репозитория         | `find…`, `count…`, `exists…`           | `findByUserId`                 |
| Событие реального времени | `домен:действие` строкой               | `feature:created`              |
| Право                     | `домен:действие`, wildcard `домен:*`   | `feature:manage`               |
| Маршрут                   | `api/v<N>/<feature>` в kebab-case      | `api/v1/feature-groups`        |
| Boolean                   | вопрос: `is`, `has`, `can`             | `isReady`, `hasAccess`         |

Имя не повторяет контекст: внутри модуля `feature` файл `dto/feature.dto.ts`, а не
`dto/feature-module-feature.dto.ts`.

## 4. Функции

- Все функции — стрелочные: `const fn = (a: A): B => {}`,
  `export const fn = async <T>(x: T) => {}`. Объявления `function` и выражения
  `function` не используются, включая хелперы модуля, type guards, фабрики и
  callback-и.
- Методы классов остаются методами. Декораторы применяются к классам и методам.
- У `const` нет hoisting: хелпер объявляется выше первого использования.
- Исключение — файлы деклараций типов и код, которым владеет фреймворк.
- Функция получает зависимости явно, возвращает предсказуемый тип и не скрывает I/O
  под именем вычисления.

## 5. Модули и public API

- Каждый модуль имеет `<feature>.module.ts` с полным списком провайдеров:
  репозитории, сервисы, контроллеры, обработчики, слушатели, bootstrappers.
- `@Injectable()` обязателен на каждом классе, который инжектируется, но сам не
  регистрирует — только `providers`.
- `index.ts` реэкспортирует то, что нужно другим модулям. Внутренние хелперы,
  приватные схемы и тестовые фабрики не экспортируются.
- Модуль регистрируется в корневом модуле один раз.

## 6. Импорты

- Внутри модуля — относительные пути.
- `core` и `common` — через их публичные индексы.
- Чужой модуль — через его `index.ts`; глубокий импорт запрещён.
- Импорты сортируются автоматически; порядок групп задаёт линтер.
- Type-only зависимости — через `import type`, когда импорт не нужен в runtime.
- Циклы между модулями запрещены; цикл через barrel-файл — тоже цикл.

## 7. TypeScript и типы

- `any` не используется там, где тип выражается безопасно; исключение — типовые
  утилиты DI и обёртки над библиотечными типами, с комментарием.
- Nullable-колонка → `| null`, не `?:` и не `undefined`.
- Ошибки типов не скрываются через `as unknown as` и необоснованные assertion.
- Тип располагается рядом с владельцем: тело запроса — в `dto/`, доменные enum-ы — в
  `<feature>.types.ts`, глобальные augmentation — только для действительно глобальных
  контрактов.
- Роли и права — const-объекты, а не enum: значения живут в БД и добавляются без
  деплоя. В ядре роли и права — просто строки; типы ролей и прав принадлежат
  модулям. В типах тел запросов — обычная строка (расширяемый `string & {}` генератор
  спецификации не выражает).
- Публичные типы экспортируются явно.

## 8. Контроллеры

- Контроллер объявляет маршрут, тег, схему безопасности, guards, схему валидации и
  делегирует сервису. Без бизнес-логики и без обращения к репозиториям.
- Маршрут — под версией API: `@Route("api/v<N>/<feature>")`.
- На каждом контроллере — `@Response<IErrorResponseDto>("default", …)`: контракт
  ошибки попадает в спецификацию.
- Каждый метод — с JSDoc и `@summary`: это документация API.
- Каждый path-параметр помечен `@Path()`; идентификатор — тип `UUID` из `core`:
  неверный формат отклоняется до контроллера.
- Статусы успеха: создание — `@SuccessResponse(201)`, действие без тела ответа —
  `@SuccessResponse(204)` и `void`.
- Контекст пользователя извлекается единственным хелпером из `core`; прямое чтение
  заголовков и состояния запроса в контроллере запрещено.
- Тело запроса типизируется интерфейсом `I<Action>Body`; тот же контракт валидируется
  схемой декоратором на методе. Деструктуризация в параметре тела не используется.
- Security-scope указывает право (`permission:<домен>:<действие>`), а не роль.
  Действие над сущностью с владельцем требует как минимум своё
  (`permission:<домен>:<сущность>:<действие>:own`); область сужает сервис.
- Возвращаемый тип — DTO, страница или примитив; тип объявлен явно, чтобы попасть в
  спецификацию.

## 9. Сервисы

- Сервис проверяет права и инварианты и бросает доменные ошибки модуля.
- Область права над сущностью с владельцем — только через правило доступа модуля
  (`<feature>.access.ts`, общий класс доступа ядра): невидимая сущность — 404
  «не найдено», видимая без права на действие — 403. Ручное сравнение владельца и
  проверка суперпользователя в сервисе не пишутся.
- Родитель, связанные и целевые сущности (в том числе инфраструктура, где действие
  исполнит привилегированный код) проверяются правом актора — берутся только из
  видимых ему.
- Несколько записей за операцию — транзакция; внутри — репозитории менеджера
  транзакции; задачи — в той же транзакции; события — после фиксации.
- Сервис возвращает DTO, а не сущность. Исключение — внутренние методы, которые
  вызываются только другими сервисами того же модуля и не выходят наружу.
- Сервис не знает о HTTP-контексте, транспорте реального времени и заголовках.
- Побочные эффекты за пределами модуля — через событие; долгие и ненадёжные — через
  задачу.

## 10. Репозитории

- Репозиторий расширяет базовый репозиторий и помечен декоратором репозитория с
  сущностью.
- Методы — только запросы и сохранение; без проверок прав и без исключений
  бизнес-уровня.
- Условия, связи и сортировки живут в методах репозитория, а не в сервисе.
- Атомарный переход состояния — условный `UPDATE` с возвратом числа затронутых строк;
  решение по результату принимает сервис.
- Общие для многих сущностей операции — в базовом репозитории `core`, а не копируются.

## 11. Сущности и миграции

- Одна сущность — один файл. Enum-ы — в `<feature>.types.ts`.
- Индексы, unique и каскады объявляются в сущности.
- Связи между сущностями разных модулей допустимы; циклический импорт файлов
  сущностей решается lazy-ссылкой в декораторе связи, а не переносом сущности.
- Сущность регистрируется в `entities` своего модуля.
- Изменение схемы — только новой миграцией; миграция генерируется, читается и
  правится до применения, добавляется в список миграций, применённая — не
  редактируется.
- Права ролей по умолчанию и смена смысла существующего права — миграция данных:
  кто имел прежнее право (роль, прямое право, scope API-ключа), получает новые;
  откат возвращает прежнее.
- Длины строковых колонок совпадают с ограничениями схем валидации.
- Секреты в БД — только хеш или шифрованное значение (ключ приложения), никогда
  открытым текстом.

## 12. DTO, валидация и пагинация

- DTO — класс, наследующий базовый DTO, с конструктором из сущности и статическим
  `fromEntity`. Вложенные DTO собираются через их `fromEntity`.
- DTO не содержит логики, кроме маппинга. Секреты наружу не выходят.
- DTO сущности с владельцем отдаёт идентификаторы и отображаемые имена владельца и
  создателя: имя — одной общей функцией, пользователи загружаются
  соединением в запросе списка, без N+1. Список таких сущностей принимает фильтр
  «мои» (`mine`).
- Схема валидации описывает форму входа: типы, обязательность, длины, форматы.
  Сообщения об ошибках — на русском.
- Схема не содержит бизнес-проверок (существование, права, статусы) — это сервис.
- Схема query перечисляет все параметры, включая `offset`/`limit` и курсор:
  результат парсинга заменяет query.
- Список — `IPaginatedDto { items, total, offset, limit }`: параметры проходят через
  `normalizePagination` (лимит по умолчанию и не больше 100), ответ собирается
  `toPage`. Лента — `ICursorPageDto { items, nextCursor }` с непрозрачным курсором.

## 13. События

- Событие — класс с `readonly`-полями в конструкторе; одно событие — один файл в
  `events/`.
- Событие несёт DTO или идентификаторы. Сущности ORM в событие не попадают.
- Слушатель подписывается в `register()` и не содержит бизнес-логики: маппинг события
  в отправку, постановку задачи или вызов сервиса.
- Входящее событие реального времени подписывается только через валидирующую обёртку
  (`onValidated`) со схемой и лимитом частоты; голая подписка не используется.
  Ошибка возвращается клиенту подтверждением с машинным кодом, а не роняет соединение.
- Новое событие реального времени сначала добавляется в типизированную карту, затем
  используется.
- События сущности с владельцем: в комнату списка — для права на все, владельцу и
  создателю с областью «свои» — лично через общий эмиттер сущностей с владельцем.
  При смене владельца бывший получает событие снятия, его комнаты пересматриваются.

## 14. Ошибки и логирование

- Доменные ошибки модуля объявляются в `<feature>.errors.ts` одним вызовом
  `defineErrors("<PREFIX>", { KEY: { status, message } })` → код `<PREFIX>_<KEY>`;
  бросается `FeatureError.KEY(details?)`.
- Без доменного смысла — исключение из единого семейства; код выводится из статуса.
  `throw new Error` в бизнес-коде запрещён.
- Статусы: форма входа — 400 `VALIDATION_ERROR`; нет прав — 403; не найдено или
  скрыто — 404; конфликт с текущим состоянием (дубликат, недопустимый переход,
  используется) — 409; лимит — 429.
- Код ошибки — часть контракта: не переименовывается без новой версии API.
  Сообщения — на русском, без внутренних деталей.
- Обязательное наличие сущности проверяется явно с исключением; `!` для подавления
  `null` не используется.
- Ошибки не игнорируются молча; пустой `catch` допустим только с комментарием,
  почему это безопасно.
- Логирование — через структурированный логгер с объектом контекста первым
  аргументом; `console.*` запрещён.
- Секреты не пишутся в логи и не попадают в сообщения исключений.

## 15. Задачи

- Обработчик — класс `<aspect>.job.ts`, реализующий контракт обработчика, с
  `definition` (очередь `домен.действие`, повторы, срок, `cron`, `tracked`,
  `external`), зарегистрированный через `asJobHandler` (`asExternalJobHandler`).
- Обработчик тонкий: достаёт данные и вызывает сервис. Данные задачи — идентификаторы
  и параметры, не сущности.
- Обработчик идемпотентен: повтор после сбоя не должен дублировать эффект.
- Постановка, связанная с изменением данных, — с `manager` транзакции.
- Ошибка без смысла повтора — `JobError(code, message, false)`.
- Долгая видимая задача сообщает прогресс и проверяет сигнал отмены между шагами.
- Периодическая работа — только `cron` очереди.

## 16. Конфигурация

- Новая переменная окружения — в схему конфигурации, в шаблон файла окружения и в
  типизированный объект. Чтение `process.env` вне `config.ts` запрещено.
- Ветвление по окружению — через флаги окружения из конфигурации; по роли процесса —
  через конфигурацию роли.

## 17. Комментарии и документация

Комментарий объясняет причину, ограничение или неочевидный контракт, а не
пересказывает код.

Допустимы:

- краткий JSDoc публичного контракта, методов контроллера (попадает в спецификацию),
  декораторов и хелперов `core`;
- объяснение неочевидного решения (порядок запуска, изоляция ошибок, retry);
- требование внешней библиотеки или платформы;
- обоснование локального исключения из правил.

Не допускаются:

- история изменений;
- закомментированный старый код;
- очевидное описание следующей строки;
- комментарий, маскирующий неверное имя или слишком сложную функцию.

Если комментарий устарел — он переписывается заново, а не дополняется.

Документация проекта (`ARCHITECTURE.md`, `MODULE-CHEATSHEET.md`, `CONVENTIONS.md`,
`CLEAN-CODE.md`, `DESIGN-PRINCIPLES.md`, `README.md`) не правится попутно с задачей.
Она меняется только в исключительных случаях — когда меняется архитектура, принцип
или паттерн проекта — и не содержит проектной конкретики. `README.md` модуля
обновляется вместе с модулем.

## 18. Тесты

- Юнит-тест проверяет наблюдаемое поведение сервиса, схемы или хелпера, а не
  внутреннюю реализацию.
- Багфикс начинается с падающего теста, воспроизводящего дефект; тест остаётся в
  кодовой базе.
- Зависимости сервиса подменяются фабриками моков из общей тестовой инфраструктуры;
  ad-hoc моки — только для того, чего в ней нет.
- Юнит-тесты не ходят в реальную БД и сеть. Тест с настоящей зависимостью
  пропускается, если её адрес не задан переменной окружения.
- Тесты не зависят от порядка запуска и очищают изменённое глобальное состояние.
- Сгенерированный код и сущности ORM напрямую не тестируются.
- **Интеграционный набор (e2e)** запускает настоящий сервер против отдельных БД,
  Redis и SMTP и проверяет сценарии по HTTP и сокетам.
  Стенд пересоздаёт только явно тестовые базы. Каждый новый эндпоинт покрывается
  сценарием: последний тест набора падает, если эндпоинт спецификации не вызван.

## 19. Линтер и форматирование

- Линтер не отключается для файла или директории ради прохождения проверки.
- Новое локальное отключение допустимо только когда правило неприменимо технически,
  причина указана рядом, а более узкого решения нет.
- Autofix используется только после просмотра затрагиваемых файлов.
- Форматирование не смешивается с несвязанным функциональным изменением.
- Ошибки lint и typecheck исправляются в рамках задачи. Новое предупреждение —
  незавершённая работа.

## 20. Исключения

Исключение должно быть:

1. вызвано требованием framework/codegen/ORM или подтверждённым техническим
   ограничением;
2. максимально узким;
3. задокументированным рядом с настройкой;
4. не расширяемым на новый код автоматически.

## 21. Проверка перед merge

Обязательный минимум — генерация маршрутов, линтер, проверка типов, юнит-тесты;
при изменении API, схемы или инфраструктуры — ещё e2e. Точные команды перечислены в
`README.md`.

```bash
<generate>    # маршруты и спецификация генерируются без ошибок и закоммичены
<lint>        # линтер: 0 ошибок
<typecheck>   # проверка типов без ошибок
<test>        # юнит-тесты зелёные
<test:e2e>    # интеграционный набор зелёный, все эндпоинты вызваны
git diff --check
```

CI дополнительно проверяет миграции на чистой БД и дрейф схемы, агента нод
(форматирование, статический анализ, тесты с детектором гонок, кросс-сборку;
версия поднята при изменении его кода, версия компилятора в образах совпадает с
манифестом),
shell-скрипты, аудит зависимостей и уязвимости образа.
