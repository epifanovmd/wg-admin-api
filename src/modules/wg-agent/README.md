# Модуль wg-agent

Связь WG-домена с агентами нод. Агент (github.com/epifanovmd/agent; сторона сервера — ядро
`src/core/agent`, REST и права — модуль [agent](../agent/README.md)) держит связь, хранит
желаемое и шлёт метрики; работу на ноде делают воркеры проекта `wg` и `socks`
([agent/README.md](../../../agent/README.md)). Модуль собирает их настройки из БД и принимает
итоги, события и метрики. Своих маршрутов и таблиц нет; контракт воркеров —
`wg-worker.contract.ts` (менять вместе с `agent/internal/contract` и манифестами воркеров).

## Настройки воркеров ноды

| Воркер/ключ     | Значение                                                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `wg/state`      | желаемое состояние: `version` (= `wg_nodes.config_version`), интерфейсы с пирами и ключами, IPIP-туннели, пробросы релея |
| `wg/probes`     | `targets` — другие ноды с `publicHost` для проб связности (`WgMeshService.probeTargetsFor`)                              |
| `socks/proxies` | `proxies` — SOCKS5-прокси ноды (`WgSocksAppService.agentConfigs`)                                                        |

`WgAgentSyncService.sync(nodeId)` собирает все три и пишет в желаемое агента
(`Agents.setConfig(…, { onlyIfChanged: true })`) — новая версия только у изменившегося
значения: агент на связи получает её сразу, без связи — при подключении (и применяет её без
связи после перезапуска). Отказ по схеме манифеста — в журнал, остальные ключи пишутся. Когда:

- **изменение домена** — `WgNodeService.markDirty` в транзакции поднимает
  `config_version`, триггер БД шлёт NOTIFY `wg_node_changed` после коммита
  (`WgNodeSignals`), процессы API (роли `api|all`) собирают настройки (изменения одной ноды
  склеиваются за 50 мс, сборки одной ноды не пересекаются);
- **нода создана, удалена, сменила адрес** — меняются цели проб у всех: сверка всех нод;
- **привязка агента** — нода получает новую версию (`bindAgent`);
- **старт процесса** и cron `wg.agent-sync` (раз в 10 мин) — сверка всех нод с агентами.

`WgAgentStateService` собирает `state` из wg-interface/wg-peer/wg-endpoint:
туннели строятся из релей-линков (`wgt<index>`, /30 из `WG_RELAY_TUNNEL_CIDR`,
MTU 1480), пробросы — из интерфейсов, обслуживаемых relay-точками ноды, и
включённых пробросов модуля wg-forward. Для интерфейса — список кандидатов
по копиям (основная, затем поднятые реплики по приоритету; закреплённая —
единственная): `dnat` и `route=direct` — прямой адрес копии, `route=tunnel` —
только туннель, `route=auto` — туннель копии, затем её прямой адрес, затем
следующая копия. Воркер wg берёт первого живого кандидата.

## Итоги, события, метрики (`WgAgentTelemetryService`)

- **Итог `wg/state`** — событие воркера `state.result` (после каждого применения):
  `{ version, appliedAt, interfaces, routes, errors }` → `appliedVersion` (только растёт;
  итог старой версии ошибку новой не перетирает), `applyError` (ошибки через «; »; нет —
  `null`), статусы интерфейсов и реплик, маршруты пробросов. Отказ воркера в настройке
  (`AgentConfigAppliedEvent` с `ok: false` — не прошла проверку) — `applyError` с его текстом.
- **Событие `route.changed`** — маршруты пробросов по пробам воркера, сразу.
- **Событие `node.info`** — версия и режим WireGuard, дистрибутив, ядро, занятые порты →
  `wgVersion` и `osInfo` ноды поверх сведений агента (`osInfoWithWorker`).
- **Метрики** (`AgentMetricsReceivedEvent`, каждая точка): `workers.wg.interfaces` (wg show
  dump) и метрики узла `host` (CPU, нагрузка, память, диск, аптайм, сетевые интерфейсы,
  conntrack) → `WgStatsIngestService`; из свежей точки ещё пробы туннелей
  (`WgLinkHealthService`), маршруты пробросов (wg-forward, обслуживающая копия), пробы нод
  (`WgMeshService`), прокси (`workers.socks.proxies`). Повтор точки (та же `at` от агента —
  пачка, ответ на которую до агента не дошёл) пропускается по отметке в Redis: старые
  счётчики после новых ingest принял бы за сброс счётчика.

## Живая статистика по спросу

`WgAgentWatchService`: пока админку кто-то смотрит (`WgViewerDemandService` — сокеты в
любом процессе), агенты нод на связи под наблюдением (`watch` в желаемом агента, срок 30 с,
продление раз в 5–15 с): метрики раз в секунду, воркеры шлют пульс с той же частотой. Уровень
журнала, выставленный страницей агента, сохраняется. Зрителей нет — наблюдение истекает само,
частота — `AGENT_METRICS_INTERVAL_MS`.
