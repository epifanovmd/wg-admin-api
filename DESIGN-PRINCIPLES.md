# Design Principles and Patterns

Как применять SOLID и паттерны без избыточной архитектуры. Общий подход к чистому
коду — в [CLEAN-CODE.md](CLEAN-CODE.md).

## Правило выбора

Паттерн применяется только к сформулированной проблеме.

Перед внедрением спроси:

1. Какая проблема уже существует?
2. Почему функция, метод сервиса или простой объект её не решает?
3. Станет ли основной сценарий понятнее?
4. Есть ли реальные варианты или внешняя граница?
5. Можно ли удалить паттерн без потери поведения?

Если проблема не формулируется, паттерн не нужен.

## SOLID

### S — Single Responsibility

Класс имеет одну ответственность и одну основную причину измениться.

Нарушение: сервис проверяет права, строит запрос к ORM, отправляет письмо и
формирует ответ для транспорта реального времени.

Исправление: права и инварианты — в сервисе, запрос — в репозитории, письмо и
доставка — в слушателях событий. Не дробить линейную операцию на десяток одноразовых
приватных методов.

### O — Open/Closed

Стабильный код расширяется добавлением варианта, а не постоянной правкой центральной
цепочки условий.

Примеры точек расширения в проекте: новый модуль в корневом модуле, новый слушатель
по токену, новый guard на маршруте, новое право в const-объекте. Пока вариантов мало и
они меняются вместе, обычный `switch` проще, чем реестр стратегий.

### L — Liskov Substitution

Каждая реализация честно соблюдает контракт:

- принимает те же допустимые входы;
- возвращает совместимый результат;
- сохраняет обещанные побочные эффекты;
- не требует скрытых условий;
- не выбрасывает неожиданные ошибки.

Все обработчики соединений и слушатели событий обязаны быть взаимозаменяемы для
инфраструктуры, которая их собирает: если реализация «не поддерживает» метод
контракта, контракт выбран неверно.

### I — Interface Segregation

Потребитель зависит только от нужной части API.

```ts
interface ISocketHandler {
  onConnection(socket: TSocket): void | Promise<void>;
}

interface ISocketEventListener {
  register(): void;
}
```

Это два контракта, а не один «участник реального времени» — у них разные потребители
и разное время вызова. Разделяй интерфейс при разных потребителях, а не ради
количества файлов.

### D — Dependency Inversion

Высокоуровневая логика зависит от контракта, инфраструктура его реализует.

Применять на границах:

- транспорт реального времени (эмиттер, а не сервер);
- почта, внешние API;
- удалённые хосты (SSH);
- часы и генераторы случайных значений — для тестов;
- инфраструктурный модуль, который собирает реализации из доменных модулей: контракт
  и токен внизу, реализации — в доменных модулях.

Контракт принадлежит потребителю. Не создавай интерфейс для каждого сервиса с
единственной реализацией: DI-контейнер и так позволяет подменить класс в тестах.

## Композиция вместо наследования

Предпочитай:

- инъекцию через конструктор для сервисов;
- декораторы для сквозного поведения маршрута (валидация, guards, security);
- события для реакции между модулями;
- Strategy-callback для взаимозаменяемого алгоритма.

Наследование допустимо при настоящем отношении «является» и стабильном базовом
контракте: базовый репозиторий, базовый DTO. Не используй его только ради повторного
использования пары методов.

## Основные паттерны

| Проблема                          | Паттерн                   | Когда применять                                    |
| --------------------------------- | ------------------------- | -------------------------------------------------- |
| Скрыть API библиотеки             | Adapter                   | Внешний API не должен протекать в модули           |
| Простой вход в подсистему         | Facade                    | Несколько шагов всегда выполняются вместе          |
| Взаимозаменяемые алгоритмы        | Strategy                  | Варианты меняются независимо                       |
| Создание зависит от окружения     | Factory                   | Выбор реализации не принадлежит потребителю        |
| Код не должен знать реализацию    | Dependency Injection      | Есть важная внешняя граница                        |
| Модули реагируют на факты         | Observer / EventBus       | Нужна подписка один-ко-многим без обратной связи   |
| Успех и отказ ожидаемы            | Исключение со статусом    | Отказ — нормальный поток, а не сбой                |
| Данные пересекают границу         | DTO                       | Наружу уходит форма, а не хранимая модель          |
| Несколько записей меняются вместе | Unit of Work / транзакция | Частичный результат недопустим                     |
| Защита маршрута с параметрами     | Guard (фабрика)           | Поведение зависит от параметров и хранит состояние |

## Практический пример: инфраструктурный модуль

Чистое разделение подсистемы реального времени:

```text
Server service     — обёртка над библиотекой, жизненный цикл
Auth middleware    — проверка токена при подключении
Client registry    — кто подключён, на скольких устройствах
Emitter service    — единственный способ отправить клиенту: адресно, в комнату, всем
Bootstrapper       — запуск, сбор handlers/listeners по токенам, остановка
Domain listener    — подписка на события своего модуля → вызов эмиттера
Domain handler     — входящие события своего модуля → проверка прав → действие
```

Здесь применяются:

- SRP — отдельные причины изменения;
- ISP — handler и listener имеют разных потребителей;
- DIP — доменные модули зависят от контрактов и эмиттера, а не от сервера;
- Adapter — детали библиотеки скрыты в сервисе сервера;
- Observer — доставка построена на событиях, сервисы не знают о транспорте.

Не нужно добавлять Factory или Strategy, пока нет нескольких способов создания или
взаимозаменяемых алгоритмов.

## Частые ошибки

- Применять паттерн ради названия.
- Создавать интерфейс для каждого класса.
- Считать любое повторение нарушением DRY.
- Добавлять абстракцию «на будущее».
- Прятать простой сценарий за generic framework.
- Использовать наследование ради нескольких общих строк.
- Создавать Strategy для единственного алгоритма.
- Делить API без разных потребителей.
- Вызывать сервис другого модуля там, где нужна реакция на событие.
- Возвращать сущность ORM вместо DTO «потому что поля те же».

## Checklist

- [ ] У паттерна есть конкретная проблема.
- [ ] Простое решение недостаточно.
- [ ] Основной сценарий стал понятнее.
- [ ] Контракт принадлежит потребителю.
- [ ] Все реализации соблюдают контракт.
- [ ] Интерфейс не заставляет потребителя зависеть от лишнего.
- [ ] Абстракция имеет реальные варианты или важную внешнюю границу.
