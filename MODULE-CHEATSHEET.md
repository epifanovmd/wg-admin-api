# Модули: архитектурная шпаргалка

Краткое руководство для ежедневных решений: где должен находиться новый код.
Архитектурная модель целиком — в [ARCHITECTURE.md](ARCHITECTURE.md), правила
написания кода — в [CONVENTIONS.md](CONVENTIONS.md).

## 1. Топология

```text
core → common          ← фундамент: контракты и реестры, ничего не знает о модулях
middleware / routing   ← сквозной HTTP-слой, ничего не знает о конкретных модулях
modules/<feature>      ← один модуль = одна предметная область или одна инфраструктурная подсистема
app.*                  ← composition root: собирает модули, запускает приложение
```

| Область      | Что здесь находится                                                                                                        | Контрольный вопрос                                         |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `core`       | декораторы, загрузчик модулей, DI-токены и реестры, базовые классы, auth, ошибки, EventBus, контракты задач, наблюдаемость | Без этого не заработает ни один модуль?                    |
| `common`     | чистые функции-хелперы                                                                                                     | Это пригодилось бы в любом другом проекте?                 |
| `middleware` | обработка каждого HTTP-запроса                                                                                             | Это должно происходить для всех маршрутов без исключения?  |
| `routing`    | генерируемые маршруты, спецификация, системные пробы и метрики                                                             | Это связывает контроллеры с сервером, а не бизнес-логика?  |
| `modules`    | доменная и инфраструктурная логика (очередь, почта, сокеты — тоже модули)                                                  | У этого есть владелец — предметная область или подсистема? |
| `app.*`      | список модулей, жизненный цикл                                                                                             | Это про сборку приложения, а не про его поведение?         |

Ядро не импортирует модули. Если ядру нужно поведение модуля — в ядре объявляется
токен и интерфейс, модуль регистрирует реализацию.

## 2. Анатомия модуля

```text
modules/<feature>/
  index.ts                     ← public API модуля
  README.md                    ← сущности, эндпоинты, события, задачи, ошибки модуля
  <feature>.module.ts          ← декларация @Module: imports, entities, providers, bootstrappers
  <feature>.entity.ts          ← сущность ORM (одна на файл; вспомогательные — свои файлы)
  <feature>.repository.ts      ← доступ к данным
  <feature>.service.ts         ← бизнес-логика
  <feature>.controller.ts      ← HTTP-контракт
  <feature>.types.ts           ← enum-ы, const-объекты, лимиты домена
  <feature>.errors.ts          ← доменные ошибки с кодами <PREFIX>_<KEY>
  <feature>.permissions.ts     ← права модуля в реестре прав (если есть)
  <feature>.config.ts          ← настройки модуля из окружения (если есть)
  <feature>.socket-events.ts   ← события реального времени модуля (если есть)
  <aspect>.job.ts              ← обработчик очереди задач (если есть)
  <feature>.handler.ts         ← обработчик входящих событий реального времени (если есть)
  <feature>.listener.ts        ← слушатель EventBus → реальное время / задачи (если есть)
  <feature>.bootstrap.ts       ← задача инициализации (если есть)
  dto/                         ← DTO ответов и интерфейсы тел запросов
  validation/                  ← схемы валидации входа
  events/                      ← классы доменных событий
  <feature>.service.test.ts    ← тесты рядом с кодом
```

Маленький модуль может не иметь части файлов; пустые директории не создаются. Модуль
без HTTP (только сервис для других модулей) — нормальная ситуация. Модуль с
несколькими контроллерами или сервисами именует их по ответственности
(`<feature>-<aspect>.controller.ts`). Реализации чужих контрактов (политика,
провайдер комнат, проба) — отдельные файлы с суффиксом роли.

## 3. Куда положить новый код

### Новый HTTP-эндпоинт

- Метод в существующем контроллере модуля-владельца → `<feature>.controller.ts`.
- Отдельная группа маршрутов той же области → второй контроллер модуля.
- Новая предметная область → новый модуль (см. раздел 7).
- Маршрут под `/api/v<N>/`; ответ по умолчанию — контракт ошибки.
- Никогда — логика в контроллере: он объявляет маршрут, security, валидацию и
  вызывает сервис.
- Маршрут, который нельзя описать контроллером (поток, подписанная загрузка) →
  провайдер маршрутов модуля; описать в README модуля.

### Новое бизнес-правило

- Правило сущности или сценария → сервис модуля-владельца.
- Правило затрагивает несколько модулей → сервис того модуля, который инициирует
  операцию; остальные реагируют на событие.
- Правило проверки формы входа (длина, формат, обязательность) → схема в
  `validation/`, а не в сервисе.
- Нарушение правила → доменная ошибка из `<feature>.errors.ts`, а не новое
  исключение по месту.

### Новый запрос к БД

- Выборка или сохранение → метод репозитория модуля-владельца сущности.
- Чтение чужой сущности из сервиса другого модуля → через репозиторий модуля-владельца,
  импортированный из его public API; свой репозиторий на чужую сущность не создаётся.
- Несколько записей за одну операцию → транзакция в сервисе, репозитории берутся из
  менеджера транзакции.
- Переход состояния, который могут выполнить параллельно → условный `UPDATE` в
  репозитории и проверка числа затронутых строк в сервисе.

### Новое поле или таблица

- Поле сущности → `<feature>.entity.ts` + новая миграция (в список миграций) +
  отражение в DTO и схеме валидации (длины должны совпадать).
- Новая сущность внутри области → отдельный файл сущности в том же модуле.
- Enum или набор констант → `<feature>.types.ts`, не в файле сущности.

### Новый ответ API

- Форма ответа → класс DTO в `dto/` со статическим конструктором из сущности.
- Тело запроса → интерфейс `I<Action>Body` в `dto/`, схема — в `validation/`.
- Список → страница по смещению из `core`; лента → страница по курсору из `core`.
- Секрет, который админ должен увидеть позже → хранится шифрованным ключом
  приложения, отдаётся отдельным эндпоинтом с правом, не в общем DTO.

### Реакция на изменение в другом модуле

- Всегда через событие: модуль-источник публикует класс события из своего `events/`,
  модуль-потребитель подписывается в своём слушателе.
- Не через прямой вызов сервиса потребителя из сервиса источника.
- Побочный эффект, который должен пережить сбой (письмо, вебхук) → слушатель
  ставит задачу, а не выполняет эффект сам.

### Фоновая или периодическая задача

- Долгая или ненадёжная работа → обработчик очереди `<aspect>.job.ts`
  (`asJobHandler`) с политикой повторов в описании; постановка — из сервиса через
  абстракцию очереди.
- Задача порождена изменением данных → постановка в той же транзакции (outbox).
- Отложенное действие (таймаут) → задача с отложенным запуском; при необходимости —
  периодическая «страховка».
- Периодическая работа (очистка, компактификация) → обработчик с расписанием
  (`cron`). Не таймер в bootstrapper-е и не ручная блокировка БД.
- Пользователь должен видеть прогресс и отменять → видимая задача (`tracked`) с
  владельцем и scope; обработчик проверяет сигнал отмены.
- Ошибка, повтор которой бессмыслен → ошибка задачи с `retryable: false`.

### Работа на удалённом хосте

- Настройка сервера, которым владеет система → агент на хосте забирает желаемое
  состояние сам (long-poll по своему ключу) и применяет его идемпотентно; сервер
  не подключается к хостам и не выполняет на них команды.
- Разовое действие на хосте → команда агенту из фиксированного набора типов;
  произвольные команды не допускаются.
- Установка на хост → фоновая задача по SSH, секреты доступа — только шифрованными
  в данных задачи.

### Сквозная HTTP-логика

- Для всех запросов (идентификатор, логирование, CORS, лимиты, разбор тела) →
  `middleware/` и порядок регистрации.
- Для конкретного маршрута (лимит на эндпоинт, HTTPS, whitelist) → guard из
  `core/guards`, применяемый декоратором на методе контроллера.
- Проверка прав пользователя → декоратор безопасности с permission-scope, а не guard.

### Новая схема аутентификации

- Новый вид вызывающего (сервис, интеграция, бот) → класс схемы в модуле-владельце,
  регистрация `asSecurityScheme`, описание схемы в конфигурации генератора маршрутов.
- Схема возвращает контекст с видом вызывающего; права проверяет по scopes.
- Ядро и другие схемы не меняются.

### Комната реального времени

- Соединение должно попадать в комнату автоматически → провайдер комнат модуля
  (`asSocketRoomProvider`).
- Клиент входит в комнату по запросу → политика комнаты (`asSocketRoomPolicy`) с
  типом комнаты и проверкой права.
- Изменение членства → слушатель вводит и выводит соединения из комнаты через эмиттер.
- Входящее событие клиента → только через валидирующую обёртку со схемой и лимитом.
- Новое событие (в обе стороны) → дополнение карт событий в `<feature>.socket-events.ts`
  модуля; общий файл контракта транспорта не правится.

### Новое право

- Объявить в `<feature>.permissions.ts` через реестр прав; использовать в
  security-scope `permission:<домен>:<действие>`. Общий список прав не правится —
  засев ролей подхватит объявленное.

### Задача при старте

- Seed, прогрев, запуск подсистемы → bootstrapper модуля, объявленный в
  `bootstrappers` его `@Module`. Некритичный объявляет `critical = false`.
- Периодическая работа — не сюда, а в очередь задач с расписанием.

### Новый параметр окружения

- Настройка платформы → схема в `config.ts`; настройка модуля → `<feature>.config.ts`
  через `defineModuleConfig` (тип и значение по умолчанию, если оно допустимо) →
  шаблон файла окружения → использование через объект конфигурации, а не через
  `process.env` в коде модуля.

### Новое письмо

- Файлы шаблона во всех локалях `templates/mail/<locale>/` + дополнение
  `IMailTemplateData` в файле письма модуля (declare module); тест полноты
  проверит наборы по локалям.

### Вспомогательная функция

- Не знает о домене и инфраструктуре → `common/`.
- Часть механики ядра (DI, auth, ошибки, события, контракты) → `core/`.
- Нужна одному модулю → внутри модуля рядом с потребителем.

## 4. Сервис или репозиторий

`repository` — как достать и сохранить: условия выборки, связи, сортировка, пагинация.
Не бросает бизнес-исключений и не знает о правах.

`service` — что можно и что должно произойти: проверка прав и статусов, инварианты,
транзакции, публикация событий, постановка задач, сборка DTO.

Если метод репозитория начинает проверять «можно ли» — он должен быть в сервисе.
Если сервис пишет условия запроса к ORM — они должны быть в репозитории.

## 5. Middleware или guard

`middleware` — сквозное поведение для каждого запроса, без знания о маршруте.

`guard` — защита конкретного маршрута, объявляемая рядом с ним. Guard может иметь
параметры (лимит, заголовок, список адресов) и собственное изолированное состояние.

Аутентификация и проверка прав — ни то, ни другое: это схема безопасности генератора
маршрутов, объявляемая декоратором на методе.

## 6. Событие, задача или прямой вызов

Прямой вызов сервиса другого модуля допустим, когда:

- результат нужен в этом же запросе для продолжения операции;
- зависимость идёт в одну сторону и не создаёт цикла.

Событие обязательно, когда:

- это реакция на факт («создано», «изменено», «удалено»), а не запрос данных;
- потребителей может быть несколько или они появятся позже;
- потребитель — инфраструктура (реальное время, почта, аудит);
- прямой вызов создал бы обратную или циклическую зависимость.

Задача обязательна, когда:

- работа долгая, тяжёлая или зависит от внешней системы;
- эффект должен пережить сбой процесса и повториться;
- работа периодическая или отложенная.

Событие публикуется после фиксации транзакции и несёт DTO или идентификаторы, а не
сущности ORM. Задача ставится в той же транзакции, что и данные.

## 7. Новый модуль: порядок действий

1. `yarn gen:module <name>` — каркас по конвенциям: сущность, репозиторий, сервис,
   контроллер, DTO, схемы, ошибки, события, модуль, README и тесты.
2. Доработать сущность → сгенерировать миграцию → добавить её в список миграций.
3. Сервис с бизнес-логикой, событиями, задачами; DTO; схемы валидации; ошибки.
4. Контроллер: маршруты под версией, security-scopes с правами, валидация тел,
   статусы 201/204.
5. При необходимости — права, обработчики задач, слушатель и обработчик реального
   времени, провайдеры и политики комнат, bootstrapper.
6. `index.ts` — только то, что нужно другим модулям.
7. Зарегистрировать модуль в корневом модуле (до модуля, собирающего реализации по
   токену).
8. Юнит-тесты сервиса и схем; e2e-сценарии для каждого нового эндпоинта.
9. Перегенерировать маршруты и спецификацию; описать модуль в его `README.md`.

## 8. Чек-лист перед merge

- [ ] Код находится в модуле-владельце, а не «где удобно»; ядро не импортирует модули.
- [ ] Контроллер только объявляет контракт и делегирует; маршрут под версией.
- [ ] Наружу уходит DTO, а не сущность; списки — единые страницы.
- [ ] Ошибки — доменные коды модуля; конфликт состояния — 409.
- [ ] Валидация входа — схемой на маршруте или событии; длины совпадают с БД.
- [ ] Реакции между модулями — через события, после транзакции.
- [ ] Фоновая и периодическая работа — задачами очереди; постановка в транзакции.
- [ ] Реальное время — через слушатель и эмиттер, не из сервиса.
- [ ] Нет импортов внутренних файлов чужого модуля.
- [ ] Новое право объявлено в реестре прав и использовано в security-scope.
- [ ] Миграция сгенерирована и просмотрена.
- [ ] Маршруты перегенерированы; lint, typecheck, юнит- и e2e-тесты зелёные.
