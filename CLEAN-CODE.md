# Clean Code Guide

Краткие правила для ежедневной разработки. Оформление кода описано в
[CONVENTIONS.md](CONVENTIONS.md), размещение по модулям — в
[MODULE-CHEATSHEET.md](MODULE-CHEATSHEET.md), SOLID и паттерны — в
[DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md).

## Приоритеты

Хороший код:

1. корректно решает текущую задачу;
2. читается без устного объяснения;
3. безопасно изменяется;
4. не содержит сложности без причины.

Принципы — инструменты, а не цель. Сначала простое корректное решение, затем
оправданная абстракция.

## Порядок работы

1. Сформулировать требуемое поведение и его владельца (модуль).
2. Определить, кто владеет данными и побочными эффектами.
3. Написать простейшее решение в нужном слое.
4. Дать предметные имена.
5. Отделить бизнес-правила от доступа к данным и транспорта.
6. Убрать подтверждённое дублирование.
7. Проверить тестами, typecheck, lint и генерацией маршрутов.

## KISS

Выбирай решение с минимальной когнитивной нагрузкой:

- ранний `return` и ранний `throw` вместо глубокой вложенности;
- обычную функцию вместо класса без состояния;
- явную последовательность шагов вместо скрытой магии;
- несколько понятных условий вместо универсального rule engine;
- локальное решение вместо преждевременного framework.

Простота — не минимальное количество строк. Иногда две именованные переменные
понятнее одного сложного выражения.

## YAGNI

Не реализуй возможность без текущего требования или существующей точки расширения.

Не создавать заранее:

- generic-сервис для одного сценария;
- base class без наследников;
- plugin system без плагинов;
- десятки неиспользуемых опций и флагов;
- слой абстракции над репозиторием ради «возможной смены ORM»;
- эндпоинты «на будущее».

Удалить ненужный код лучше, чем хранить его «на будущее».

## DRY

DRY относится к знанию, а не к одинаковой форме кода.

Выносить общее, когда:

- повторяется одно бизнес-правило;
- исправление требует синхронно менять несколько мест;
- копии обязаны вести себя одинаково.

Не объединять, когда:

- сходство случайно;
- сценарии развиваются независимо;
- общая функция получает много флагов;
- невозможно дать абстракции предметное имя.

Небольшое повторение безопаснее неправильной абстракции. Два похожих метода
репозитория в разных модулях — нормально; одно правило доступа, скопированное в два
сервиса, — нет.

## Имена

Имя выражает смысл в предметной области:

```ts
// Плохо
const data = await repo.find();
const manager = new DataManager();

// Лучше
const activeMembers = await memberRepo.findActiveByChatId(chatId);
const sessionService = new SessionService();
```

- функция и метод — глагол;
- boolean — вопрос: `isReady`, `canEdit`, `hasAccess`;
- коллекция — множественное число;
- имя не повторяет уже очевидный контекст;
- избегай `manager`, `helper`, `common`, `utils`, если нельзя уточнить
  ответственность.

## Функции и методы

Функция должна:

- выполнять одну связную операцию;
- работать на одном уровне абстракции;
- получать зависимости явно;
- возвращать предсказуемый тип;
- не менять входные данные без контракта;
- не скрывать I/O под именем вычисления.

Чистая функция предпочтительна, когда задача является вычислением (проверка права,
разбор токена, расчёт пагинации).

Много boolean-параметров скрывает смысл:

```ts
// Плохо
sendNotification(userId, true, false);

// Лучше
sendNotification(userId, { silent: true, retry: false });
```

Если опции выбирают разные алгоритмы, используй отдельные методы или Strategy.

## Слои

Каждый класс отвечает за один уровень:

```text
Controller  — контракт HTTP и делегирование
Service     — бизнес-правила и транзакции
Repository  — доступ к данным
Listener    — реакция на события и доставка
Entity      — схема данных
```

Сигналы нарушения: контроллер строит запрос к БД; репозиторий бросает «нет доступа»;
сервис читает заголовки; слушатель принимает бизнес-решения.

Выноси хелпер или приватный метод, когда логика:

- повторяется;
- имеет отдельное предметное имя;
- мешает читать основной сценарий сверху вниз.

Не выноси только ради уменьшения файла.

## Побочные эффекты

У побочного эффекта должен быть явный владелец жизненного цикла:

- запись в БД — в транзакции сервиса;
- доставка клиенту — в слушателе, после фиксации;
- подписка на события — в `register()`, снятие — при остановке;
- таймер и периодическая задача — запуск в bootstrapper-е, остановка в `destroy`;
- повторная инициализация безопасна либо запрещена контрактом.

Не запускай I/O внутри функции, имя которой обещает только вычисление.

## Ошибки

Ошибка обрабатывается один раз на подходящем уровне:

- репозиторий не ловит;
- сервис бросает осмысленное HTTP-исключение или перебрасывает с контекстом;
- middleware превращает исключение в ответ и логирует 5xx;
- обработчик событий изолирует свою ошибку и не роняет остальных.

Не превращай ошибку в `null`, если `null` означает отсутствие данных. Ожидаемый
отказ («не найдено», «нет доступа», «конфликт») выражается исключением с правильным
статусом, а не флагом в ответе.

## Асинхронность

- `await` каждого промиса, результат которого важен; fire-and-forget — только через
  EventBus или с явным `.catch` и логом.
- Параллельные независимые операции — `Promise.all`/`allSettled`, а не
  последовательный `await` в цикле.
- Транзакция короткая: без сетевых вызовов и ожидания внешних сервисов внутри.
- Долгие операции не блокируют ответ: результат доставляется событием.

## Когда рефакторить

Сигналы:

- одно изменение требует правок в нескольких несвязанных модулях;
- невозможно дать методу короткое имя;
- класс меняется по разным причинам;
- растёт число флагов и ветвлений;
- тест требует слишком много моков;
- наружу постоянно импортируют внутренние файлы модуля;
- поведение опасно менять из-за скрытых побочных эффектов.

Сначала зафиксируй поведение тестом. Меняй структуру небольшими шагами и не смешивай
рефакторинг с новым поведением без необходимости.

## Checklist

- [ ] Основной сценарий читается сверху вниз.
- [ ] Имена выражают предметный смысл.
- [ ] Нет возможностей без требования.
- [ ] Каждый класс на своём слое.
- [ ] Дублируется знание, а не просто похожие строки.
- [ ] Побочные эффекты видимы, имеют владельца и снимаются.
- [ ] Ошибка обрабатывается на одном уровне.
- [ ] Абстракция упрощает основной сценарий.
- [ ] Поведение покрыто соразмерной проверкой.
